# DATA_MIGRATION_PLAN.md — SQL Server → PostgreSQL (DRAFT)

Status: **Draft** — DB-02..DB-06 and D-014 password strategy are complete; OQ-6/OQ-8/OQ-9/OQ-4 and
the remaining data reconciliation work are still open. **No migration has been or will be executed
during planning.**

## 1. Principles

1. **Two-step migration to PG**: (a) schema definition (Prisma-first, validated types), (b) data ETL preserving legacy IDs.
2. Legacy systems read-only during cutover period; no dual-write (a parallel-run with reconciliation is planned instead).
3. Every migration step has a reconciliation query and rollback point.
4. Source of truth for cutover: a **snapshot backup of SQL Server** restored to an isolated migration DB — never the production or UAT instance itself.

## 2. Scope (phase 1)

In: identity/auth tables (users, tokens obsolete after cutover), role/user-type/menu tables, master tables (department, site, role, parameter, configurations, shift master, weekly-off, holidays), employee master + dependants, documents + document types + file metadata, message catalog, email templates/config.

Out (until later phases): leave, payroll, muster, DataInput temp tables/processes, external LinkId mappings (PMS push mapping — flag: needed for auto-login links parity).

## 3. Schema conversion approach

- Define the new PostgreSQL schema via Prisma with explicit `@map` names and preserved legacy IDs; the Phase-2 draft is `prisma/schema.prisma` and has passed `prisma validate`.
- Preserve legacy primary/foreign keys (IDs) verbatim; use `GENERATED BY DEFAULT AS IDENTITY` and set high-water marks from legacy identity values post-load.
- Type conversion per table in §4 mapping (values, not just types: check bit→boolean semantics, date/timestamp conversion to UTC if D-006 chooses `timestamptz`, string trimming rules for legacy trailing space behavior).
- TVP patterns (`MenuItemType`, `DependantType`, `InsertDocumentType`, `InsertExtraColumnType`) become batched inserts inside service transactions (used by new app, not by ETL).
- Stored procedures (~145 total; phase-1 subset) decomposed per the strategy in DATABASE_DISCOVERY.md §5; each phase-1 proc's behavior gets a parity mapping (input params → service, tables touched, outputs/messages). Remaining out-of-scope proc bodies are deferred.

## 4. Data-type specifics (draft, validation pending)

- NVARCHAR → TEXT/VARCHAR: preserve Unicode; watch out for trailing spaces and NVARCHAR empty-string vs NULL conventions in legacy (SS stores '' exactly; PG may need explicit handling).
- BIT → BOOLEAN (0=false, 1=true, NULL=NULL).
- DATETIME → if wall-clock semantics retained: `timestamp without time zone` (safer to match legacy UI dates DD/MM/YYYY + local server timezone); if normalized: `timestamptz` — **requires rule on how legacy `TimeZone` header factored into calculations** (**OQ-8**).
- UNIQUEIDENTIFIER → UUID (Token rows obsolete — new session model; do not migrate).
- Decimal/money columns out of phase-1 but documented as `numeric(p,s)`.
- IDENTITY/sequences — set via `setval()` after load.

## 6. Reconciliation & validation

Per workstream: row-count checks + checksum(m) on key columns + spot-check queries (documented, parameterized, read-only against both systems). Reconciliation runbook to be produced after DB-02/DB-06. Downtime-free strategy replaced by **cutover window** (below).

## 7. Cutover plan (draft)

1. Freeze legacy (announce read-only window).
2. Snapshot SQL Server backup → migration instance (isolated).
3. Run ETL to staging PG; run reconciliation suite.
4. Restore file directory to private storage; verify docs openable via signed URLs.
5. Deploy NestJS + Next.js (staging first, prod plan same steps).
6. Smoke tests (login rule matrix, master CRUD, doc upload/download/expiry job).
7. Cut DNS/endpoint switch; enable new monitoring; keep legacy app **available but read-only** for N weeks (rollback point).
8. Password strategy from D-014 executed here (server-side legacy verification plus mandatory change, then bcrypt/argon2).

## 8. Rollback / recovery

- Rollback point = DNS flip back to legacy app (read-only data preserved during freeze).
- Migration DB steps are idempotent scripts; failed run reruns from snapshot copy.
- Since legacy data untouched, catastrophic rollback = legacy app + SQL backups.
